# KEEP IT LIT - feature-specific gotchas

Moved out of CLAUDE.md on 11 Oct 2026. The general gotchas stay in CLAUDE.md; these are the ones tied to one feature or art pack.

- **The escape hatch is a kit template too (F80).** `InteractableKit.escapeHatch` (optional slot, built by **KEEP IT LIT > Build > Interactables**) is a double-leaf trapdoor made of two Alchemist `WoodDoor01` leaves over a `Glow` slab. `MazeEscape.BuildHatch` clones it, gives `Glow` the runtime `HatchGlow` material (so `ApplyLockLook`'s green/red still works) and swings the `LidL`/`LidR` children about their local Z: shut while padlocked, ajar (16°) once usable, thrown open (100°) on entry. With the trapdoor present, stepping on the hatch runs `MazeEscape.EnterHatch` instead of the instant `CompleteEscape`: freeze, leaves open, the player eases over the opening looking down (0.75 s), then `FloorCleared` starts the blackout while they are lowered `dropStartDepth` through it (0.45 s); `_entering` holds the timer and trigger meanwhile, and the routine bails if a capture starts first. A black `Pit` inset makes the open hatch read as a hole. Empty slot = the old glowing slab and instant drop. The exit gates (F111) are the kit template `InteractableKit.escapeGate` (not optional: `ProjectSetup.EmptySlots` flags it; built by `InteractableKitBuilder.EscapeGate.cs`, primitives and the kit materials, never null). **Name contract**, found by name: `PostL`/`PostR`/`Lintel` (colliders), `Shutter` (slats + one solid box over the opening, moves up ~3 m), `LeverBox` (`GateLever` is added to it at runtime) with `LeverFocus` (solid box collider, hit by `PlayerInteractor.Probe`, which stays focusable for an `IProgressInteractable` even when `CanInteract` is false so the prompt can say NO POWER/LOCKED) and `LeverHandle`, `Lamp0`-`Lamp2` (a `Bulb` renderer and a disabled `Light` each), `Chain`, `Stairwell`, `StubLight`; local +Z points into the maze. The lever hold is **non-resetting**: `IProgressInteractable.HoldTick` is driven by `PlayerInteractor` and never decays, unlike `HoldSeconds`. `MazeGenerator.ChooseGates` checks the kit slot and theme **before** the walls are built (a missing slot keeps the hatch; a hole must never be left in the wall), and `ReserveGates`/`IsLayoutReserved` keep props off the cells.
- **`MazeDoor._open` is intent, set when a slide starts, not when it ends.** It used to flip only at the end of the slide coroutine, so mid-slide every reader saw a stale value: `CheckBash` re-bashed a door that was already rolling up every frame (restarting the slide and renewing `AIFollower.Stall` forever — the hunter froze for good in front of a shutter that looked open), and `Unlock`/`AllStarsCollected` arriving while a bashed door rolled back down did nothing and left it shut but `_permanentlyOpen`. The physical state is the panel offset (`_blocker.enabled = _panelOffset < 2`). Doorway-occupied checks read the whole `DoorBreakers` registry (`BreakerInDoorway`), so a shutter never closes on the Stalker either, and a bash-hold that expires with someone in the gap retries every 0.5 s instead of giving up.
- **F74's new statics follow the same reset rule.** `RunRules` (current rule/name/description/multipliers) and `LoreArchive` (read note ids) both have a `[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]` reset; `LoreArchive` is also cleared in `GameFlow.ReturnToMenu` (campaign-scoped, like `PlayerWallet`) while `RunRules` is recomputed every floor by `ApplyFloorProfile` regardless (still cleared there too, for cleanliness). `ThrowController`'s carried count and `Lantern`'s carried state are deliberately **not** statics — they're instance fields on components a scene reload naturally recreates, which is what makes them reset "for free" without touching this rule.
- **F87's statics follow the same reset rule.** `ContractState` (active contract, floor, the two offers, salesman line) has a `[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]` reset and is cleared in `GameFlow.ReturnToMenu`. It is saved in `SaveData` as `contractActivePlus1` / `contractFloor` / `contractOfferAPlus1` / `contractOfferBPlus1` (ids stored +1, so a pre-F87 save - fields missing, read as 0 - means "none"; `SaveSystem.Version` was not bumped). `GameFlow.IsInIntake` is reset in `Reload`, `ResetStatics` and (through `Reload`) `ReturnToMenu`; `IntakeRoom.Active` is a scene-scoped reference cleared in `OnDestroy`. `ContractTracker` and `ThrowController`'s carried count are instance state and reset by a scene reload; its three static-event subscriptions (`LoreNote.Read`, `Stalker.PlayerTouched`, `ThrowableItem.HunterInvestigated`) unsubscribe in `OnDestroy`.
- **`FloorProfile.Objective` is a flag set now (F77), not the single `FloorObjective` value it used to be.** `Objective.Stars` is gone — stars are always present — so test a mechanic with `profile.Has(Objective.Lockdown/Blackout/KeyHunt)`, never equality against `Objectives`. `GameFlow.RolledObjectives` (the previous floor's rolled pair, so two consecutive floors never repeat) follows the same static-reset rule as everything else in the first Gotcha above: reset in `ResetStatics` and `ReturnToMenu`. `RunRules.HashSeedFloor` is `internal` (not `private`) specifically so `FloorProfile.RollObjectives` can reuse it with its own salt — the two rolls are deliberately independent draws from the same seed, not the same draw read twice. `+18` is `BuildKeys`' RNG offset — the next free one is `+19`. The padlock itself (locked hatch or gates, red glow, wayfinding retarget to the nearest missing key) lives entirely in `MazeEscape`, not in `GameOutcome` or `GameManager`.

Spec: `plannings/alchemist-maze-dressing-plan.md`.

The packs are git-ignored: `/Assets/Socket Pack/` and `/Assets/Gabies_Assets/` joined the ignore block, and the DeadBody LITE meshes/materials/textures the new prefabs use were force-added.
