# KEEP IT LIT - systems reference

Moved out of CLAUDE.md on 11 Oct 2026 (it was over the 150k-character limit). CLAUDE.md keeps a one-line index; this file holds the full notes, one bullet per system, unchanged. If something here disagrees with the code, the code is newer.

## The authored rooms and galleries

**Almost nothing is authored in the scene.** `MazeGenerator.Awake` (`[DefaultExecutionOrder(-100)]`) builds the entire game at runtime: walls, floor, ceiling, the NavMesh bake, the stars, the first-person rig, the flashlight, and every director component, each `AddComponent`-ed onto the `MazeGenerator` GameObject and wired with a `Configure`/`Bind` call. The main authored piece is **the shop room**: a `ShopRoom` object at (−92, 5, −45), west of the maze, that is real scene geometry you can select and edit. **Since 10 Oct 2026 it is a hand-editable prefab, `Assets/Prefabs/ShopRoom.prefab`** (the salesman inside is the nested `ShopSalesman.prefab`): change the shop in Prefab Mode — nothing overwrites it. `ShopRoomBuilder.BuildSilently()` / Build Missing Pieces only *place* the prefab when the room is missing (or save a plain scene room as the prefab, `ShopRoomBuilder.SaveAsPrefab`, in `ShopRoomBuilder.Prefab.cs`); **KEEP IT LIT > Build > Shop Room (regenerate)** (`Assets/Editor/ShopRoomBuilder.cs`; materials in `Assets/SourceFiles/Materials/Shop`) is a confirmed reset that regenerates from code and overwrites the prefab. The add-to-existing migrations (contract board, door hinge, Timmy) still edit the scene instance; apply their overrides to the prefab. **F78:** the room is a 9 × 12 × 3 m alchemist's shop dressed from the `Assets/BK_AlchemistHouse` pack (architecture scaled ×1.2, every prop placed by renderer bounds because many pack pivots are off-centre, pack colliders/rigidbodies stripped in favour of builder-made `BoxCollider`s, 7 lights max); the dressing passes and a `ShopRoomBuilder.Audit(root)` self-check live in the `partial` file `ShopRoomBuilder.Dressing.cs`, `ShopRoomBuilder.BuildSilently()` rebuilds without dialogs, and `AlchemistMaterialUpgrade` (`Assets/Editor/AlchemistMaterialUpgrade.cs`, idempotent, no menu item) is the pack's one-off Built-in → URP conversion, run automatically by every builder that uses the pack. Spec: `plannings/shop-room-alchemist-plan.md`. The salesman is **Timmy** (10 Oct 2026; it was the Adam pack's Guard): a stripped `PlayerRobot.prefab` (`ShopRoomBuilder.Timmy.cs`, ProjectSetup piece "Shop salesman (Timmy)" swaps an old Guard in place) on `Animation/Shop/ShopTimmy.controller` — Idle (Starter Assets), Talk (Mixamo `Talking.fbx`) and Wave (Mixamo `Waving.fbx`, optional: copied from the shared library when it is there, re-run Build Missing Pieces to add the state). `ShopkeeperAnimator` (on `Salesman`) plays them: `ShopRoom.Open` and walking up to the counter `Greet()` (wave, 8 s cooldown; a 2 s talk without a Wave clip), `SetTalking` while the shop/contract menu is open; He is the hand-editable prefab `Assets/Prefabs/ShopSalesman.prefab` (builders only place it once it exists) and wears the brass **Shopkeeper** skin (`HunterSkinBuilder.Shopkeeper.cs`, same UV-space painter as the Orderly via `GenerateSkin`; aged brass, verdigris seams, amber eyes; menu **Build > Shopkeeper Skin (repaint)**, textures in `Characters/Shopkeeper/`; the plain TimmyRobot material is swapped, any other hand-set material is kept); `ShopRoom.headPivot` is his Humanoid Head bone, turned in `LateUpdate` as a yaw offset on top of that frame's animated pose (a plain non-animated pivot still works). Without it `MazeGenerator` logs an error and clearing floors 1–4 falls back to a plain win. **Leaving the shop (F84)** mirrors the hatch walk-in: E at the door → `ShopRoom.WalkOutRoutine` freezes the player, swings the leaf out on `ShopRoom.doorHinge` (a pivot on the leaf's edge made by `ShopRoom.CreateDoorHinge`; the builder wires it, and an older scene without it gets one at runtime from `Door/WoodDoor01…`), eases the player up to the doorway looking through it, then on through it while the screen and the shop hum fade out → `GameFlow.NextFloor()`. The swing direction is picked at runtime so the leaf always opens away from the room. No leaf at all = the old plain fade (`DescendRoutine`). **The leaf must not be Static** — the shop room is otherwise all-static, and static batching merges a static leaf into a combined mesh at scene load, after which the hinge turns but nothing moves on screen. `ShopRoomBuilder.MakeMovable` clears the flags on the hinge; Check Project flags a static leaf and Build Missing Pieces fixes it in place. The same applies to anything else in an authored room that has to move at runtime. **The pack's `Architecture/Door` model is the frame and a closed panel fused into one mesh** — it can never open and it hides the `WoodDoor01` leaf, so the builder only uses it to measure where the leaf goes and then deletes it (the `IntWall01door` wall module already frames the opening); Check Project flags a leftover one and Build Missing Pieces removes it. `IsInShop` stays true through the walk-out (cleared by the reload), so the maze HUD doesn't pop back up mid-walk.

Another authored-once piece is **the interactables gallery** (F72/F73/F74/F75): an `InteractableKit` object holding one live instance each of the shutter door, wall button, battery cell, fuse box, and (F74) the bottle/can throwables, glass/puddle noisy-floor patches, lantern, lore note and the four theme interactables (call bell/steam valve/candles/terminal), plus (F75) **the Stalker** — the player's own robot body (`Assets/Prefabs/PlayerRobot.prefab`), instantiated, unpacked and stripped down to its visuals — that `MazeGenerator.BuildDoors`/`BuildFuses`/`BuildThrowables`/`BuildNoisySurfaces`/`BuildLantern`/`BuildLoreNotes`/`BuildThemeInteractables`/`BuildStalker` clone for every maze. Generated once by **KEEP IT LIT > Build > Interactables** (`Assets/Editor/InteractableKitBuilder.cs`, build-missing-only by default — each slice only adds its own slots). Without it, or with a slot missing, `MazeGenerator` logs an error naming the menu item and skips just that feature for the run (doors/buttons/vaults, fuses, throwables, noisy floors, the lantern, notes, theme interactables, or the stalker — whichever slot is missing).

The second authored piece is **the floor-theme gallery** (F41): a `FloorThemes` object north of the maze at (−70, 5, −6) with one `FloorTheme` row per floor, each holding live prefab instances of that floor's wall, pillar, floor tile, ceiling tile, lamp, locker and props. Generated once by **KEEP IT LIT > Build > Floor Themes** (`Assets/Editor/FloorThemeBuilder.cs`; assets under `Assets/SourceFiles/Themes/<n>_<Name>/`, never overwritten on a rebuild unless you choose *Replace everything*). At Play, `MazeGenerator.ResolveTheme` picks the row for `FloorProfile.ThemeIndex` and **clones the scene instances** (so unapplied overrides count), then deactivates the gallery. Without it, or with an incomplete row, it logs an error and builds the old primitive maze. Look owns colour, fixtures and prop density (`FloorTheme`); gameplay numbers such as lamp intensity and range stay in `FloorProfile`. Spec: `plannings/floor-themes-plan.md`.

## Systems

- **World** — `MazeGenerator` (~790 lines): seeded maze, runtime `NavMeshSurface` bake, star placement, actor placement, and the composition root described above. `UsedSeed` is the seed actually used (Inspector `seed`, a pending retry seed, or `Environment.TickCount`); it is logged and shown on the end screen. **(The F48 kit maze, START NEW MAZE and the Maze Modular Puzzle Kit theme were removed 10 Oct 2026.)** **Maze dressing (F70):** a private `MazeDressing` view, resolved once by `ResolveDressing()` right after `ResolveTheme()`, is what every prop/decal/set-piece pass reads (never `_theme` directly) — themed floor → `_theme`'s dressing fields; primitive fallback → all-default (empty), so an un-rebuilt scene spawns nothing new. Three new passes (+9 and +10 once belonged to the removed kit-only passes and are now unused; nothing was renumbered), each its own RNG offset from `usedSeed` so the existing carve/star/lamp/locker/prop/shard streams (+0…+5) are untouched: `BuildSetPieces` (+8, pre-bake — reserves its cell, and `_propWalls`/`_setPieceCells` bookkeeping so wall/ceiling props skip it), `BuildFloorProps` (+6, post-bake, collider-less floor clutter) and `BuildDecals` (+7, post-bake, alpha-clipped analytic-placement quads — no raycasts). **Blood decals (7 Oct 2026):** the code-drawn blood splat/smear/pool textures are replaced by `Assets/Blood decal pack` (its own materials are Built-in shaders, so only the textures are used). `BloodDecalUpgrade` (`Assets/Editor/`, idempotent, runs at the end of Build > Floor Themes, flagged by Check Project) makes one transparent URP Lit material per texture under `Themes/Common/Materials/BloodPack`, switches the shared `BloodSplat`/`BloodSmear`/`BloodPool` materials in place, and adds a `DecalVariants` component (materials + aspect ratios) to every `*_Blood*` prefab; `BuildDecals` → `ApplyDecalVariant` picks one by a hash of `(x, z, i, wall/floor)` — no rng draw, so the +7 stream is unchanged — and reshapes the quad so the variant's longest side equals the placed size. Density is `MazeGenerator.decalDensity` (×2: theme chances capped at 0.9, +1 decal per cell) and `bloodWeight` (×3 pick weight for pieces with `DecalVariants`) — both only change the +7 decal stream. **Set-piece wall decals:** `BuildSetPieces` puts a set piece's pivot ON the wall face with +Z into the cell, so a set piece's wall decal goes at `FloorThemeBuilder.WallDecalInset` (0.02), not the old 1.98 that hung them 2 m out in mid-air; `SetPieceDecalFix` (same hooks as `BloodDecalUpgrade`) re-seats old prefabs and reshapes their shared-blood quads to the texture's aspect. **No footprints** (7 Oct 2026): the builder no longer makes `*_Footprints` decals and `BloodDecalUpgrade` turns old ones into blood pools (free roll). **Corpses:** the shared `FallenRunner` set piece's capsule body is replaced by the six `Assets/DeadBody LITE/Prefabs/Body_Only` bodies (`CorpseUpgrade.AddBodies`, used by the builder and to migrate the existing prefab; laid along the wall, seated by renderer bounds, pack rigidbodies stripped, box colliders kept); one is active per placement via `ModelVariants`, applied in `BuildSetPieces` by a cell hash (no rng draw, +8 stream unchanged). Only the pack files the game references are in git (force-added; both pack folders are otherwise ignored — see `.gitignore`). Transparent decal materials must keep `_BlendModePreserveSpecular` = 0: URP re-validates it to premultiplied alpha otherwise and the torch's specular lights the whole quad as a pale rectangle. Built by **KEEP IT LIT > Build > Floor Themes** (now `FloorThemeBuilder` split across `FloorThemeBuilder.cs` and the `partial` file `FloorThemeBuilder.Dressing.cs`, which holds the shared texture/decal/particle helpers and the common prop/set-piece/dust set). Re-run both (Keep existing assets) and save the scene to get the new content; an un-rebuilt scene plays exactly as before. Spec: `plannings/maze-dressing-plan.md`. **Darkness pass (F71):** the per-floor lamp/fog/ambient numbers live in `FloorProfile.For` (`CellsPerLamp` Blend(5,8), `LampIntensity` (1.0,0.7), `LampRange` (5.0,4.0), `Ambient` scalar (0.015,0.006), `FogDensity` (0.07,0.12)) and apply to the primitive fallback directly — but a **themed** floor (1–5 normally) reads `_theme.Ambient` instead (`ResolveTheme`), so the scene's `FloorTheme.ambient` rows need their own pass: `DarknessRelight` (`Assets/Editor/DarknessRelight.cs`, no menu item) scales every `FloorTheme.ambient` down so its brightest channel is 0.012, via `SerializedObject` (idempotent — a row already at or under the target is left alone). It runs automatically at the end of **KEEP IT LIT > Build > Floor Themes**; after a hand edit to `FloorTheme.ambient`, **KEEP IT LIT > Check Project** flags it and **Build Missing Pieces** relights it. Lamp fixture emission dropped to `lampColor * 1.2` (star stays at `* 2.5` so it still reads as the thing worth finding); stars also pulse ±30 % at 0.5 Hz (`StarPulse`, attached in `AttachStarLight`). **Doors, buttons & vaults (F72):** `MazeGenerator.BuildDoors` (+11 for placement, +15 for vault loot; runs post-bake, after `SpawnStars` and before `SpawnShards`) clones `InteractableKit`'s `shutterDoor`/`wallButton`/`batteryCell` templates. Security-door candidates are found by BFS: `ReachableCells(start, blocked)` treats one passage as closed and checks whether the start side then loses a star cell — only a bridge passage (the maze is braided by `RemoveDeadEnds`, so most aren't) qualifies, preferring a 3–40 % cut-off region. Its button lands on a free wall (`IsFreeWall`: not in `_propWalls`, not near a lamp) **in sight of the door** — a cell in a straight open line from the cell in front of it, at most `buttonSightCells` (4) away, else that cell itself, else (logged) anywhere ≥3 BFS steps into the start side (10 Oct 2026: an out-of-sight Lockdown button made a floor unwinnable without the hunter bashing the door). Vaults never use the hunter's spawn cell (`FarthestCell`), which A10's kept dead ends had made a common vault spot. Because the maze is braided, bridge passages are rare and that search often places nothing, so both passes fall back to **sealing a cell**: a shutter on every opening of a star's own cell (or, for a vault, a two-opening cell), accepted only if `ReachableCellsAvoiding(start, cell)` still reaches every other cell. The shutters are chained through `MazeDoor.LinkedDoor` (one-way; `Unlock` propagates), and one button opens the whole chain. The timed conversion walks the chain too, so a timed star room rolls down together. A vault is a dead-end cell (`WallCount == 3`), or that sealed-cell fallback, turned into the same kind of locked room, plus a `BatteryCellPickup` and 2 of the floor's own shards forced inside via `_vaultForcedShardCells`, read by a modified `SpawnShards`/`BuildShard` (shard count and caps unchanged — the forced ones are subtracted from the normal pool, not added). Manual doors gate nothing; `FloorProfile.ManualDoors`/`SecurityDoors`/`Vaults`/`HasTimedDoor` are per-floor tables like `Footprints`. Missing/incomplete `InteractableKit` → `LogError` naming **KEEP IT LIT > Build > Interactables**, and doors/buttons/vaults are skipped entirely (no primitive fallback, per decision D11). Spec: `plannings/darkness-and-interactivity-spec.md`, slice F72. **Objectives, fuses & hatch variants (F73, flags since F77):** `FloorProfile.Objectives` (`[Flags] enum Objective { None = 0, Lockdown = 1, Blackout = 2, KeyHunt = 4 }`, tested with `FloorProfile.Has(Objective)`) is the floor's mechanic *set*, not a single value — floor 1 is always `None` (stars only, the teaching floor); every floor from `FirstRolledFloor` (2) on rolls exactly `MechanicsPerFloor` (2) of the three from the seed (`FloorProfile.RollObjectives`, a pure function of `(UsedSeed, floor)` salted apart from `RunRules`' own roll so a Retry keeps its pair and the two rolls never correlate), excluding whatever pair `GameFlow.RolledObjectives[floor - 1]` was so two consecutive floors are never identical. `Has(Blackout)` sets `FuseCount = 3` and knocks 2 off `StarCount`; `Has(KeyHunt)` sets `KeyCount` (2 on floors ≤3, else 3) and knocks 1 off; both trims share one final `Max(2, StarCount)`. `Has(Lockdown)` sets `HasTimedDoor` (folding in the old `HasTimedDoorTable`). `MazeGenerator.debugObjectives` (Inspector, a flags mask) forces a floor's pair for testing, bypassing the roll (and not writing `RolledObjectives`) — `None` means "roll normally". **Key Hunt (F77):** on a `KeyHunt` floor, `MazeGenerator.BuildKeys` (+18, post-bake, after `BuildFuses` and before the +13 throwable/notes passes) scatters `KeyCount` brass keys (`KeyPickup`, cloned from `InteractableKit.keyPickup`) on free walls, the same decreasing-`minSeparation` placement loop as `BuildFuses`. `KeyRing` (an *instance* component on the player, same pattern as `ThrowController` — see the Player bullet) is the single source of truth for `Held`/`Total`/`Changed`; its `Total` comes from however many keys actually got placed (decision: gate on what was placed, not `FloorProfile.KeyCount`), so an undersized maze still locks behind what it could fit. `MazeEscape` is `Locked` for the whole escape when `KeyRing` is incomplete: a Hatch's trigger does nothing but play a padlock clunk and show `LOCKED · h / t KEYS` (at most every 2 s); a Lift's ring fills nothing and shows `LIFT LOCKED · h / t KEYS`. While locked the escape ping/chevron retarget to the nearest missing key (`KeyRing.TryNearestMissing`) instead of the hatch, and the hatch/lift light + glow material turn red (`MazeEscape.ApplyLockLook`, same red language as a fuse box's indicator) until `KeyRing.Changed` reports `IsComplete`, at which point a `"THE HATCH/LIFT IS UNLOCKED"` subtitle shows and the normal path resumes — `CompleteEscape` is still the single exit. Keys are deliberately neither a `Pickup` nor an `ObjectiveToken` (see the Gotchas entry below): they never gate the hatch *opening*, only its use. `TensionDirector` appends a third `KEYS h / t` counter segment when `KeyRing.Total > 0`; Fuse Map (shop item) also beacons every key and the Star Compass points at untaken ones. `FloorIntroBanner`'s objective line is now built from a list (`FIND n STARS`, then `RESTORE n FUSES` / `FIND n KEYS FOR THE HATCH` / `SECURITY LOCKDOWN` for whichever mechanics are set), joined with ` · `. Spec: `plannings/key-hunt-plan.md`. `MazeGenerator.BuildFuses` (+12, post-bake, after `BuildDoors`) scatters `FuseCount` fuse boxes (far apart, off the start/star/door/vault cells, on a free wall like a button), then runs a **multi-source BFS from every fuse cell at once** so every cell (and, via a parallel `_lampCells` list, every lamp) belongs to whichever fuse reached it in the fewest steps. On a Blackout floor every lamp starts `SetPowered(false)` and the start cell gets one static red emergency light; a `FuseBox` (`IInteractable`, hold 2 s) powers its whole sector back on in a ripple (`WallLamp.SetPowered(true, steps * 0.12s)` per lamp) and completes an `ObjectiveToken` (see the Escalation bullet). `AIFollower.BindTorch(Flashlight, Transform camera)` (wired in `SetUpAtmosphere`) makes the hunter notice the torch beam itself landing on it (angle/range/LOS against the beam's own blended shape, 6 s cooldown, `HearNoise` 40 m) even without full sight. `MazeEscape` (+17, seeded off `UsedSeed` alone so a retry keeps its choice) makes floors 3–5 a 50 % chance of a **Lift** instead of a Hatch: an 8 s-to-fill 2 m ring (decays at half rate outside it, HUD `LIFT ARRIVING n%`, first entry `HearNoise` 60 m) that completes through the exact same `DropThroughHatch` → `GameOutcome.FloorCleared`/`Win` path as the Hatch trigger. **Stealth tools, lore, theme interactables, run rules (F74):** all post-bake, after `BuildFuses`. `BuildThrowables`/`BuildNoisySurfaces` share one `+13` stream (`ThrowableItem`/`NoisySurface` clones on plain cells); `BuildLoreNotes`/`BuildThemeInteractables` share `+14` (2 notes per floor, ids `(floor-1)*2 + {0,1}`, text verbatim in `plannings/darkness-and-interactivity-spec.md`; theme interactables keyed off `FloorProfile.ThemeIndex` — Ward→call bell, Boiler→steam valve, Crypt→candles ×2, Lab→terminal — skipped on the primitive fallback); `BuildLantern` is `+15` (its own `System.Random`, sharing only the numeric offset with `BuildDoors`' vault-loot stream, never the same instance). All four wall-mounted kinds share `TryPickFreeWallCell`/`TryPlaceOnFreeWall`, the same free-wall test `PlaceButtonFor`/`BuildFuseBox` use. `RunRules` (static, `Resolve(usedSeed, floor)` hashed so a retry keeps its floor's rule, floor ≥ 2) is resolved inside `ApplyFloorProfile` — before its `useFloorProfile`-off early return — and `ApplyToProfile` mutates the already-blended `FloorProfile` fields (`HearingScale`, `FogDensity`/`ViewDistance`, `PhantomInterval`, `ShardCount`/`WalkSpeed`) right after `PlayerInventory.ApplyActiveModifiers`; effects with no home on the profile (`DyingGrid`'s 60 s lamp kill via a `MazeGenerator` coroutine, `WeakBattery`'s `Flashlight.SetStartFraction`/`SetRechargeMultiplier`, `GlassFloors`' `NoisyPatchMultiplier`, `KeenEars`' `ShardPayoutMultiplier` read by `PlayerWallet.CollectMazeShard`, `Restless`'s `DreadDirector.SetHardMinimumCooldownMultiplier`) are read straight off `RunRules` by whichever system needs them. `FloorIntroBanner` (RuntimeUi, built/`Show`n last in `SetUpAtmosphere`) waits out the title screen itself (polls `GameFlow.IsRunActive` on unscaled time) before its 5.5 s fade-in/hold/fade-out.
- **Player** — `FirstPersonRig` builds the camera and head-mounted `Flashlight` (F key, flicker, `InputEnabled` so endings can take the torch away). **F71 darkness pass:** the beam is wide by default and narrows/brightens to a focused beam while RMB / gamepad LT is held (`IsFocused`, `FocusBlend` 0..1, eased over 0.15 s of scaled `Time.deltaTime`); `Range`/`OuterAngle` always return the current blended value, so anything testing "is X in the beam" stays correct mid-blend. Focused drain is ×1.5 (`focusedDrainMultiplier`); `SetRangeMultiplier(float)` is a hook for the Focus Lens shop item (F75, unused so far) that scales only the focused end of the range blend. The battery is no longer a one-shot resource: while off (or dead) for more than 2 s it recharges 1 s of charge per 3 s off, capped at 60 % (never fully, so a Spare Battery still matters), blocked while `GameOutcome.IsOver`; `IsDead` therefore clears itself once recharge brings `SecondsLeft` back above zero — don't cache "dead" as permanent. `Drain(float fraction)` removes battery directly (F75's Stalker touch). `PlayerStealthState` derives `NoiseRadius` from actual `CharacterController` velocity and exposes `VisibilityMultiplier` (driven by the torch: `TorchVisibility`, written every frame by `Flashlight` from its focus blend, `Lerp(0.85, 1.25, FocusBlend)` — a focused beam is more telling than a flat 1 used to be). Movement is still `ThirdPersonController` (Starter Assets, namespace `StarterAssets`) with `FirstPerson = true`; it owns `MovementLocked`, `LockCameraPosition` and `LookAt(worldPoint, turnFraction)`. **Interaction (F72):** `PlayerInteractor` (added to the player by `SetUpAtmosphere`, `[DefaultExecutionOrder(-10)]`) is the one system every `IInteractable` (door, button, vault battery cell, and later fuse boxes/notes) goes through — a camera spherecast finds the nearest one in range, E presses it (or fills a hold via `IInteractable.HoldSeconds`), and `PlayerHud.SetFocusPrompt` overrides whatever `Locker.SetPrompt` last set while something is focused. `Locker` does **not** implement `IInteractable`; it keeps its own E handling in `Update` but yields the press to `PlayerInteractor.HasFocus` (now a parameter on `Locker.Bind`) while not already occupied, so a closer door/button/pickup always wins. **`PlayerInteractor.Fallback` (F74):** something that has taken over E without being under the crosshair (a carried `Lantern`, an open `LoreReadingUi`) sets `who.Fallback = this` and clears it when its own state ends; `Update`'s `_focused == null` branch calls it instead of doing nothing, so "E with no focus" (put the lantern down, close the reading panel) needs no second E reader. **`ThrowController` (F74)** is an *instance* component (added by `SetUpAtmosphere`, not a static) so a fresh, empty one exists every scene load — carries up to 3 bottles/cans, G/gamepad right shoulder throws the most recently picked one via `ThrowableItem.Launch` (solid collider + `Rigidbody` while flying, trigger at rest so the `CharacterController` never kicks it); a bottle shatters into a `NoisySurface.SpawnGlassShatter` glass patch, a can settles and reverts to pickable. `PlayerStealthState.SurfaceNoiseMultiplier`/`EnterSurface`/`ExitSurface` (ref-counted — two overlapping patches never stack, the loudest wins) is what `NoisySurface` drives; `MinVisibility` is the analogous floor for `Lantern`'s carried +0.8. `PlayerStamina.SprintBlocked` (ORed with `Exhausted`) is what carrying the lantern sets. **`KeyRing` (F77)** is the same kind of *instance* component as `ThrowController` — added by `SetUpAtmosphere`, no execution-order attribute needed, no static, no reset rule: a scene reload recreates it empty, which is exactly "resets every floor" for free. Holds `Held`/`Total`/`Changed` and `TryNearestMissing`; see the World bullet's Key Hunt note for how `MazeEscape`/`TensionDirector`/`ConsumableController` all read it.
- **Hunter** (no nickname; it was called the Weeping Angel until 6 Oct 2026, when the name moved to Stan — `AngelAudio` and `plannings/weeping-angel-spec.md` are the hunter's and keep the old name) — `AIFollower` (~1500 lines): sight cone + LOS, hearing, last-known-position search sweep, patrol bias toward uncollected stars, wander points, `SetThreatLevel(progress, hunting)` escalation dial. Events: `ChaseStateChanged(bool)`, `AmbushStateChanged(bool)`, `PlayerCaught`. Capture still happens only in `Chase`. The red is built eyes anchored off the `Head` bone (`AIPresence.BuildEyes`/`SetFaceMode`) — there is no face plate (removed F47, 21 Sep 2026). The F44 stare/gaze state (a bounded rush to a corner vantage point and a watch that froze while looked at) was removed 22 Sep 2026 as clunky; only its ambush sibling remains. **Since 11 Oct 2026 the hunter wears the Sci-Fi Cyborg** (`Assets/Cyborg/Cyborg_APose.fbx`, Mixamo rig imported Humanoid, katana and unskinned pistol left out, URP materials made by `HunterBodyBuilder.Cyborg.cs`; only the files the scene uses are force-added, the folder is git-ignored); **KEEP IT LIT > Build > Hunter Body Look > Cyborg / Orderly robot** switches and rebuilds (an Editor preference, default Cyborg; Build Hunter Body and Check Project follow it). Speeds are measured on whichever body is built. The Orderly robot below is the alternative look. **The Orderly: Timmy in a "Hospital orderly" skin (F102, 10 Oct 2026):** the editor menu item **KEEP IT LIT > Build > Hunter Body** (`Assets/Editor/HunterBodyBuilder.cs`, dialog-free `BuildSilently()`, ProjectSetup piece "Hunter body (Orderly robot, F102)") puts a stripped `PlayerRobot.prefab` instance (`InteractableKitBuilder.StripRobotToVisuals`, scale 1.05, child `HunterBody`) under the `AIFollower`, wires `HunterGaze`, `eyeHeight` and the `locomotion*Speed`/`maxWalkPlayback` fields, and rebuilds `Assets/SourceFiles/Animation/Hunter.controller`. - **Contracts (F87)** — optional side jobs the salesman offers between floors. `ContractState` (static, campaign-scoped: `ActiveId`/`ActiveFloor`, the shop's two `OfferA`/`OfferB`, a transient `SalesmanLine`; ids are indexes into its def table - append only) holds what the shop offers and what was taken. Offers are rolled in `GameOutcome.FloorClearSequence` from a hash of (`UsedSeed` of the floor just cleared, floor) *before* the shop checkpoint, so a shop resume (which rebuilds a maze with a new seed) shows the same pair from the save. Taking one (`ShopMenu.OpenContracts`, opened by E at the **contract board** on the shop's south wall - `ShopRoom.contractZone`, added to an existing room by `ShopRoomBuilder.AddContractBoard` / the ProjectSetup piece "Shop contract board") sets `ActiveFloor = shopFloor + 1` and writes a shop checkpoint. `ContractTracker` (an *instance* component on the player, added by `SetUpAtmosphere` like `KeyRing`; `outcome.BindContracts`) checks it on that floor from existing signals - `PlayerStealthState.Hidden` (Never hide), `AIFollower.PlayerCaught` + static `Stalker.PlayerTouched` (Not a scratch), torch + controller velocity (Walk in the dark, 60 s), `PlayerWallet.ShardsFoundThisAttempt` vs the placed `ShardPickup`s (Take what glitters, 60%), static `LoreNote.Read` (Read it all; voided if the floor placed no notes, as is Scavenger with no shards), the run clock (Don't dawdle: 4 + floor minutes), static `ThrowableItem.HunterInvestigated` (Make some noise, twice - an impact the not-already-chasing hunter heard) and `ThirdPersonController.IsSprinting` (Light feet).
